[10주차](/posts/linux-systems-week10-memory-management/)에서는 물리 메모리를 node·zone·page로 나누고, buddy allocator가 빈 페이지를 관리하는 과정을 봤다. 이번에는 **프로그램의 주소가 실제 데이터에 도달하는 과정**을 살펴본다. 이어서 파일의 페이지를 찾는 데도 쓰이는 XArray를 배우고, 이를 함수 호출 집계에 활용한다.

Drive의 `week11`에 있는 주소공간 강의와 `Practical Class 10`을 함께 정리했다. **11주차와 실습 번호 10은 서로 다른 번호**다. 아래의 주소 예제는 강의가 가정한 x86-64·5단계 페이징을 따르고, 실습 출력은 자료에 실린 Linux `5.4.214syslab` 환경의 예다. 이 글에서 새로 커널 실습을 수행한 결과는 아니다.

## 1. Anonymous page: 원래 파일이 없는 데이터

*Address Space 2~4쪽*

프로세스의 heap과 stack처럼, 어떤 파일의 특정 위치에서 읽어 온 것이 아닌 데이터를 담는 페이지를 **anonymous page**라고 한다. `mmap(MAP_ANONYMOUS)`로 만든 영역이나 private mapping의 copy-on-write로 생긴 페이지도 대표적인 예다.

강의는 익명 영역에 처음 쓰고, 메모리 압박으로 내보냈다가 다시 읽는 흐름을 보여 준다.

1. 유효한 익명 영역에 처음 쓸 때 page fault가 발생할 수 있다.
2. 커널이 페이지를 준비하고 페이지 테이블에 연결한다. 쓰기가 수행되면 데이터가 바뀐다.
3. 내용을 보존하면서 RAM을 회수하려면 swap에 저장할 수 있다. 이때 PTE에는 RAM의 프레임 대신 swap 위치를 찾을 정보가 남는다.
4. 같은 주소를 다시 접근하면 fault 처리로 내용을 불러오고 매핑을 복구한다.

중요한 것은 **다시 가져온 물리 프레임이 원래 프레임일 필요가 없다는 점**이다. 프로세스가 계속 사용하는 가상주소와 실제 RAM의 위치를 분리했기 때문에 가능한 일이다.

강의 표의 “회수 전에 swap에 기록”은 보존해야 할 익명 페이지의 내용을 전제로 읽는다. 모든 익명 페이지가 반드시 swap으로 이동한다는 뜻은 아니다. Swap이 없거나 페이지를 회수할 수 없는 조건에서는 이 경로를 그대로 사용할 수 없다.

## 2. File-backed page: 다시 읽어 올 원본이 있다

*Address Space 3~4쪽*

File-backed page는 파일의 내용과 연결된다. 일반적인 buffered I/O에서 파일 내용을 RAM에 보관하는 **page cache**가 여기에 해당한다.

```text
write(fd, buf)
  → 사용자 버퍼에서 page cache로 복사
  → 파일 페이지를 dirty로 표시
  → writeback으로 저장장치의 파일에 반영
  → clean 상태가 되면 필요에 따라 캐시에서 회수
  → 나중에 cache miss가 발생하면 파일에서 다시 읽기
```

보통의 buffered `write()`는 데이터가 page cache에 전달된 뒤 반환할 수 있다. 반환했다는 사실만으로 저장장치에 지속적으로 기록되었다고 볼 수는 없다. 동기 I/O 옵션과 `fsync()` 같은 동기화 경로는 별도로 고려한다.

Clean file-backed page는 파일에서 다시 읽어 올 수 있으므로, 내용을 swap에 복사하지 않고 RAM에서 버릴 수 있다. 반면 dirty page는 변경 내용을 보존하는 처리가 필요하다.

| 구분 | Anonymous page | File-backed page |
|---|---|---|
| 대표적인 내용 | heap·stack·익명 매핑 | 파일의 캐시·파일 매핑 |
| 다시 읽어 올 곳 | 보존해 둔 swap 내용 등 | 원래 파일 |
| 회수할 때의 핵심 | 파일 원본이 없으므로 내용을 보존할 방법이 필요 | clean이면 버리고 다시 읽을 수 있음 |
| 구분할 대상 | 프로세스의 가상 영역 | 파일 안의 위치 |

**보충 예시:** 파일에서 읽은 내용을 사용자 공간의 `buf`에 복사했다면, 파일의 page cache 페이지와 `buf`가 들어 있는 익명 페이지는 별개다. 같은 값이 담겨 있어도 역할과 회수 방법이 다르다. `MAP_PRIVATE` 파일 매핑도 쓰기로 CoW가 발생한 페이지는 익명 페이지가 될 수 있다.

## 3. struct page는 데이터를 담는 페이지가 아니다

*Address Space 5~6쪽*

`struct page`는 물리 페이지 프레임을 설명하는 **관리 정보**다. 페이지 프레임은 실제 데이터가 들어가는 RAM의 공간이다.

```text
struct page                         물리 페이지 프레임
┌─────────────────────┐            ┌─────────────────────┐
│ 상태·참조 수·목록 연결 │ ── 설명 ─→ │ 프로그램/파일 등의 데이터 │
└─────────────────────┘            └─────────────────────┘
   강의 예: 64 bytes                    강의 예: 4 KiB
```

두 크기는 강의의 예제 조건이다. `struct page`의 크기와 필드 배치, 기본 페이지 크기는 커널 설정과 아키텍처에 따라 달라질 수 있다.

| 정보 | 읽는 관점 |
|---|---|
| `flags` | dirty, locked, LRU 등 페이지 상태와 구성에 따른 부가 정보 |
| `mapping` | 파일 또는 익명 메모리와 연결되는 정보 |
| `index` | 해당 페이지가 연결된 객체 안에서의 위치 |
| `_refcount` | 페이지의 수명 관리에 쓰는 참조 수 |
| `_mapcount` | 사용자 페이지 테이블 매핑 수를 추적하는 정보 |
| `private` | 페이지를 사용하는 하위 시스템의 용도별 정보 |

강의 표에서 `mapping = anon_vma`라고 쓴 부분은 관계를 설명한 것이다. 실제 필드는 상태에 따른 비트 표시와 해석 규칙이 있으므로 항상 평범한 `anon_vma *`로 바로 역참조하는 포인터라고 받아들이지 않는다. 파일의 `index`도 디스크의 물리 블록 주소가 아니라 **파일 내부의 페이지 위치**를 나타낸다.

### 상태가 바뀌면 목록에서의 역할도 바뀐다

강의는 `lru`, `buddy_list`, `pcp_list`가 union 공간을 공유하는 모습으로 설명한다.

- **Buddy 목록:** 아직 할당하지 않은 블록을 크기별로 관리한다.
- **Per-CPU page 목록:** 빈 페이지 일부를 CPU 가까이 보관해 할당·반납 경로를 줄인다.
- **LRU 목록:** 사용 중인 파일·익명 페이지 중 회수 후보를 관리한다.

같은 페이지를 이 목록들에 동시에 아무렇게나 연결하는 것이 아니다. 기존 역할을 끝내고 필요한 상태 변경을 거쳐 다른 목록으로 옮긴다. LRU에 있다는 것은 “빈 페이지”라는 뜻도 아니다.

이 목록의 필드 이름과 잠금 구현은 커널 버전에 따라 다르다. 여기서는 자료의 상태 전환을 이해하는 데 집중한다.

## 4. vmemmap과 PFN: 메타데이터에서 물리 위치 찾기

*Address Space 7쪽, 11~14쪽*

**PFN(Page Frame Number)** 은 물리 페이지 프레임의 번호다. 4KiB 페이지라면 프레임의 시작 물리주소는 `PFN × 4096`, 즉 `PFN << 12`다.

강의의 `vmemmap`은 `struct page`들을 가상주소상 연속된 배열처럼 다루는 모델이다.

```text
PFN 0  ↔ vmemmap[0] ↔ 물리주소 0x0000의 프레임
PFN 1  ↔ vmemmap[1] ↔ 물리주소 0x1000의 프레임
PFN 2  ↔ vmemmap[2] ↔ 물리주소 0x2000의 프레임
```

단, 물리주소 공간에는 장치의 MMIO 영역 같은 **hole**이 있을 수 있다. 모든 PFN이 일반 RAM을 가리키거나, 모든 위치에 사용 가능한 페이지가 있다고 가정해서는 안 된다.

128GiB RAM을 4KiB씩 나누면 페이지는 다음 개수다.

$$
\frac{128\cdot 2^{30}}{2^{12}}=33{,}554{,}432.
$$

각 프레임의 관리 정보가 64B라고 단순 계산하면 메타데이터만 2GiB다. 실제 구성은 hole과 메모리 모델 등을 고려해야 하지만, 관리 정보도 RAM을 소비한다는 점을 보여 준다.

### 강의의 PFN 계산 예제

강의는 다음 값을 가정한다.

| 항목 | 값 |
|---|---|
| `vmemmap` 시작 가상주소 | `0xffd4000000000000` |
| 관심 있는 `struct page`의 가상주소 | `0xffd4000000000080` |
| `sizeof(struct page)` | `0x40`, 즉 64B |

바이트 차이는 `0x80`이고, 배열 원소 크기로 나누면 PFN은 2다.

$$
\mathrm{PFN}=\frac{\texttt{0x80}}{\texttt{0x40}}=2,
\qquad
\mathrm{PA}=2\times2^{12}=8192=\texttt{0x2000}.
$$

C에서 `struct page *` 포인터끼리 뺀 결과는 이미 **원소 개수**다. 바이트 주소 차이를 구했을 때 나누는 `sizeof(struct page)`를 포인터 차이에 다시 나누면 틀린다.

## 5. 물리주소를 포인터로 캐스팅하면 되는가?

*Address Space 11~14쪽*

`0x2000`이라는 물리주소를 알았더라도 `(char *)0x2000`으로 접근하면 CPU는 이를 **가상주소 0x2000**으로 해석한다. 일반적인 커널 코드도 메모리를 가상주소로 접근하기 때문이다.

강의의 direct map 예제에서는 물리주소에 다음 시작주소를 더한다.

```text
direct-map base              0xff11000000000000
물리 프레임의 시작주소        +              0x2000
프레임 내용을 보는 가상주소    0xff11000000002000
```

이 가상주소를 접근할 때도 TLB나 페이지 테이블을 통한 주소 변환은 존재한다. **Direct map은 주소 변환 하드웨어를 건너뛴다는 뜻이 아니다.** 물리 메모리를 일정한 대응 관계로 매핑한 커널 가상 영역이라는 뜻이다.

이때 구별할 주소는 세 가지다.

| 주소 | 가리키는 것 |
|---|---|
| `0xffd4000000000080` | PFN 2를 설명하는 `struct page` 메타데이터 |
| `0x2000` | PFN 2 프레임의 물리 위치 |
| `0xff11000000002000` | PFN 2의 데이터에 접근하는 direct-map 가상주소 |

`alloc_pages()`가 반환하는 `struct page *`도 첫 번째 종류다. 반환값을 곧바로 사용자 데이터 버퍼처럼 쓰는 것이 아니라, 적절한 매핑·변환 수단을 통해 프레임 내용에 접근한다.

위 시작주소는 5단계 페이징 강의 예제의 값이다. 실제 시스템에는 4단계 구성도 있고 메모리 주소 무작위화도 적용될 수 있으므로 하드코딩할 상수가 아니다. [Linux 5.4의 x86-64 메모리 배치 문서](https://www.kernel.org/doc/html/v5.4/x86/x86_64/mm.html)

## 6. 5단계 페이징과 canonical address

*Address Space 8~10쪽*

64비트 주소값을 담을 수 있다고 해서 모든 비트 조합이 유효한 가상주소인 것은 아니다. 강의는 **57비트 가상주소를 사용하는 5단계 페이징**을 가정한다.

이 구성의 canonical address는 bit 63~57이 bit 56과 같아야 한다. 부호 확장 형태를 갖추므로 낮은 주소 영역과 높은 주소 영역 사이에 non-canonical 구간이 생긴다.

| 구간 | 시작 | 끝 |
|---|---|---|
| Low canonical | `0x0000000000000000` | `0x00ffffffffffffff` |
| Non-canonical | `0x0100000000000000` | `0xfeffffffffffffff` |
| High canonical | `0xff00000000000000` | `0xffffffffffffffff` |

Low와 high는 각각 64PiB이며, 두 영역을 합친 canonical 주소 공간은 128PiB다. 이는 설치된 RAM의 양이 아니다. 주소 형식이 canonical이어도 실제 매핑이나 접근 권한이 없을 수 있다.

Linux의 5단계 지원 설정을 켠 커널도 4단계 하드웨어에서 부팅할 수 있다. 그때는 `P4D` 계층이 접힌다. 따라서 강의의 “57비트”를 모든 x86-64 Linux 환경의 고정값으로 외우면 안 된다. [Linux 5.4의 5-level paging 문서](https://www.kernel.org/doc/html/v5.4/x86/x86_64/5level-paging.html)

### TLB miss와 page fault는 다르다

```text
가상주소
  → TLB에서 최근 주소 변환을 확인
      ├─ hit: 변환과 권한에 따라 접근
      └─ miss: 페이지 테이블 탐색
                 ├─ 유효한 매핑: 변환을 얻어 접근
                 └─ 페이지 부재/권한 문제 등: page fault 처리
```

TLB는 최근 변환을 빠르게 찾는 캐시다. **TLB miss가 곧 디스크 접근이나 page fault는 아니다.** 페이지 테이블에 유효한 매핑이 있으면 탐색으로 해결할 수 있다.

Page fault도 항상 실패를 뜻하지 않는다. 처음 사용하는 유효한 영역에 페이지를 준비하거나 swap에서 불러오는 정상적인 처리일 수 있다. 반대로 허용되지 않은 주소나 권한 위반이면 새 페이지를 무조건 할당해 주지 않는다.

## 7. 주소의 비트가 페이지 테이블을 고른다

*Address Space 9~10쪽, 15쪽*

4KiB 페이지를 쓰는 5단계 예제에서 주소의 구성은 다음과 같다.

```text
부호 확장  PGD    P4D    PUD    PMD    PTE    페이지 내부 offset
  7비트    9비트  9비트  9비트  9비트  9비트       12비트
```

CR3가 최상위 테이블의 물리 위치를 찾는 출발점이 되고, 각 단계의 9비트가 512개 항목 중 하나를 고른다. 다음 테이블로 이동하는 순서는 **PGD → P4D → PUD → PMD → PTE**다. 마지막 항목에서 프레임 위치를 얻고 페이지 안의 offset을 더한다.

강의의 `0xff11000000002000`은 이 구성에서 다음 인덱스로 나뉜다.

| PGD | P4D | PUD | PMD | PTE | offset |
|---|---|---|---|---|---|
| 273 | 0 | 0 | 0 | 2 | 0 |

인덱스만으로 물리주소가 결정되지는 않는다. 각 단계에서 실제로 어떤 테이블과 프레임을 연결했는지도 알아야 한다. 강의 그림은 그 연결을 가정해 물리 프레임 `0x2000`에 도달하는 예를 보여 준다.

주소의 하위 12비트는 여기서 **페이지 내부 offset**이다. PTE에 저장되는 present·접근 권한 등의 flag 비트와 혼동하지 않는다. Huge page를 쓰면 중간 단계에서 큰 프레임으로 연결할 수 있으므로 모든 매핑이 끝까지 같은 형태로 내려가는 것도 아니다.

### 왜 하나의 큰 배열로 만들지 않을까?

57비트 주소 공간에서 4KiB 페이지의 개수는 $2^{45}$개다. 모든 가상 페이지에 대해 8B 항목 하나를 미리 두면 다음 크기가 필요하다.

$$
2^{45}\times 8\mathrm{B}=2^{48}\mathrm{B}=256\mathrm{TiB}.
$$

프로세스가 그 주소 공간을 거의 사용하지 않아도 이 거대한 배열을 마련해야 한다. 다단계 페이지 테이블은 **사용하는 주소 영역에 필요한 하위 테이블만 마련**해 이런 낭비를 줄인다.

각 테이블에 8B 항목 512개를 두면 `8 × 512 = 4096B`이므로 테이블 하나도 4KiB 페이지에 맞는다. 주소공간이 커서 테이블을 여러 단계로 나눈다는 사실과, 실제 데이터가 여러 페이지에 나뉜다는 사실을 구분한다.

## 8. 같은 가상주소, 달라질 수 있는 물리 프레임

*Address Space 16쪽*

강의의 마지막 그림은 가상주소 `0x4000`을 예로 든다.

```text
회수 전:    VA 0x4000 → PFN 100
회수 후:    VA 0x4000 → 현재 RAM에 없음, 내용은 swap/파일에 보존
재접근 후:  VA 0x4000 → PFN 850
```

프로세스의 포인터는 그대로지만, 커널은 실제 내용을 다른 위치로 옮길 수 있다. 가상 메모리를 단순히 “RAM보다 큰 메모리를 쓰는 기법”으로만 보면 이 연결을 놓치게 된다. 주소를 물리 위치에서 분리하는 것이 페이지의 회수·재배치·재적재를 가능하게 한다.

## 9. XArray: 큰 정수 인덱스로 객체 찾기

*Practical Class 10, 3~10쪽*

앞에서는 파일의 페이지를 `파일 + 페이지 위치`로 구별했다. 이런 인덱스로 객체를 찾는 데 쓰이는 자료구조가 **XArray(eXtensible Array)** 다. 개념적으로는 큰 포인터 배열처럼 사용할 수 있지만, 가능한 모든 인덱스의 저장 공간을 처음부터 확보하지 않는다.

예를 들어 `index 2 → 객체 A`, `index 67 → 객체 B`, `index 155 → 객체 C`만 저장할 수 있다. XArray는 인덱스의 비트를 따라 필요한 노드로 내려간다. Page cache가 중요한 사용처이며, 이번 실습에서는 CPU 번호나 태스크 번호로 호출 횟수 객체를 찾는 데 이용한다.

XArray의 anchor인 `struct xarray`에는 잠금, 동작 설정, 시작 항목인 `xa_head`가 있다. 내부 노드 `struct xa_node`를 볼 때는 다음 필드가 중요하다.

| 필드 | 의미 |
|---|---|
| `shift` | 이 노드의 슬롯 하나가 담당하는 인덱스 범위의 크기를 정함 |
| `offset` | 부모 노드에서 자신이 연결된 슬롯 번호 |
| `count` | 이 노드 안의 비어 있지 않은 슬롯 수 |
| `nr_values` | value entry 및 관련 sibling entry의 수 |
| `parent` | 부모 내부 노드 |
| `array` | 소속 XArray |
| `slots` | 자식 노드 또는 저장 항목으로 이어지는 배열 |

`count`는 그 노드 아래에 저장된 모든 객체의 총수가 아니다. 자식 노드 두 개만 연결된 내부 노드라면, 각 자식 아래의 객체가 많아도 `count`는 2일 수 있다.

실습의 일반적인 설정은 `XA_CHUNK_SHIFT = 6`, 즉 노드당 64슬롯이다. 슬롯 번호는 **0~63**이다. 자료 9쪽 그림의 마지막 `slots[64]` 표기는 64개의 슬롯을 설명하는 문맥에서는 `slots[63]`으로 읽어야 한다.

일반 포인터 저장에는 정렬 조건이 있다. `kmalloc()`처럼 조건을 만족하는 포인터와 임의의 정수를 캐스팅한 포인터를 같은 것으로 취급하지 않는다. 정수 값은 `xa_mk_value()` 같은 value-entry 표현을 사용한다. [Linux 5.4 XArray 문서](https://www.kernel.org/doc/html/v5.4/core-api/xarray.html)

## 10. 인덱스 64를 넣으면 왜 높이가 달라질까?

*Practical Class 10, 11~15쪽*

자료는 인덱스 0부터 순서대로 넣는 예제로 트리의 성장을 설명한다.

1. 빈 XArray의 시작은 `NULL`이다.
2. **인덱스 0의 항목만** 있다면 시작 위치에 항목을 직접 표현할 수 있다.
3. 인덱스 1을 추가하면 슬롯을 가진 노드가 필요하다.
4. 인덱스 0~63은 `shift = 0`인 노드의 64개 슬롯에 들어간다.
5. 인덱스 64를 추가하면 새 상위 노드와 다음 구간의 하위 노드가 필요하다.

```text
상위 노드: shift = 6
  slots[0] → 하위 노드: index 0~63, shift = 0
  slots[1] → 하위 노드: index 64~127, shift = 0
                 slots[0] → index 64의 객체
```

여기서 상위 슬롯 하나는 $2^6=64$개의 인덱스를 담당한다. 인덱스 67이라면 상위에서는 `67 >> 6 = 1`, 하위에서는 `67 & 63 = 3`을 사용한다.

**보충 계산:** 67은 두 번째 하위 구간의 네 번째 슬롯이다. `shift`는 슬롯 수 자체를 뜻하지 않는다. 노드당 슬롯 수가 64여도, 어느 높이에 있느냐에 따라 슬롯 하나가 담당하는 인덱스 범위가 달라진다.

자료의 첫 항목 직접 저장 그림은 인덱스 0 예제다. 처음 넣은 값이 큰 인덱스인 경우까지 “첫 항목이면 언제나 노드가 없다”고 일반화하지 않는다.

## 11. XArray API의 반환값 구별하기

*Practical Class 10, 16~19쪽*

| 함수 | 역할 | 확인할 결과 |
|---|---|---|
| `xa_load(xa, index)` | 정확한 인덱스 조회 | 해당 항목, 없으면 `NULL` |
| `xa_find(...)` | 시작 인덱스부터 조건에 맞는 항목 탐색 | 항목과 갱신된 인덱스 |
| `xa_insert(...)` | 빈 인덱스에만 새 항목 삽입 | 성공 0, 이미 있으면 `-EBUSY`, 할당 실패 가능 |
| `xa_store(...)` | 해당 인덱스의 항목 저장·교체 | 이전 항목 또는 오류를 표현한 반환값 |
| `xa_erase(...)` | 해당 인덱스 제거 | 이전 항목 |

`xa_store()`는 “빈 곳에만 넣기”가 아니다. 기존 항목을 교체할 수 있으므로 중복 삽입을 막으려는 코드에 무심코 사용하면 안 된다. 반환값도 단순한 성공 여부 정수가 아니다. 오류는 `xa_err()` 또는 `xa_is_err()`로 확인한다.

또한 `xa_erase()`는 인덱스와 항목의 연결을 없애는 작업이다. 그 포인터가 가리키는 객체를 누가 언제 해제할지는 별도의 수명 관리 문제다. `xa_destroy()`도 사용자가 저장한 모든 객체를 알아서 `kfree()`해 주는 함수가 아니다. [Linux 5.4 XArray의 Normal API](https://www.kernel.org/doc/html/v5.4/core-api/xarray.html#normal-api)

## 12. ds_monitoring: 매번 출력하는 대신 집계하기

*Practical Class 10, 20~32쪽*

커널 함수가 수백만 번 호출될 때마다 `printk()`를 하면 로그를 읽기 어렵고 계측 자체의 비용도 커진다. 실습의 `ds_monitoring`은 **호출 중에는 키별 횟수를 모으고, 나중에 한꺼번에 출력**하는 도구다.

| 구성 | 저장하는 것 |
|---|---|
| `ds_monitoring` | XArray, 전체 횟수 `total_counts`, 콜백 묶음 |
| `ds_monitoring_elem` | 키, 이름, 해당 키의 횟수 `count` |
| `ds_monitoring_operations` | 키 추출·이름 추출·한 항목 출력 함수 |

콜백을 바꾸면 집계 기준도 바뀐다. `get_index()`가 PID를 반환하면 태스크별 통계, CPU 번호를 반환하면 CPU별 통계가 된다. 이름을 사용하지 않는 실습에서는 `get_name`을 생략할 수 있다.

매크로의 역할도 나뉜다.

- `DEFINE_DS_MONITORING`: XArray와 콜백 묶음, 실제 집계 객체를 정의한다.
- `DS_MONITORING_INIT`: 객체 필드의 초기값을 구성한다.
- `DECLARE_DS_MONITORING`: 다른 파일에서 이미 정의한 객체를 참조하기 위한 선언이다.

호출 흐름을 순차 실행의 의사코드로 쓰면 다음과 같다. 아래는 개념 설명이며 동시 실행에 안전한 완성 코드가 아니다.

```text
key = get_index(target)
entry = XArray에서 key 조회

entry가 있으면:
    entry.count += 1
없으면:
    key와 count = 1을 가진 객체를 준비해 등록

total_counts += 1
```

출력 때는 존재하는 항목들을 순회하며 `count × 100 / total_counts`를 계산한다. 사용을 끝낼 때는 각 항목이 가진 이름·객체의 메모리와 XArray 내부 구조를 정리한다.

### XArray 내부 잠금이 집계 전체를 보호하지는 않는다

자료의 29~30쪽 코드는 동작을 이해하는 출발점이다. 그대로 일반적인 동시 실행 코드의 완성형이라고 보면 다음 문제를 놓친다.

**같은 키를 처음 등록하는 경쟁:** 두 실행 흐름이 모두 `xa_load()`에서 없는 항목을 봤다고 하자. 각각 객체를 만든 뒤 `xa_store()`하면 나중 저장이 앞선 객체를 교체할 수 있다. 개별 API가 내부 잠금을 사용해도, “조회 → 없으면 생성 → 저장”이라는 여러 단계가 하나의 원자적 작업이 되지는 않는다.

**할당·저장 실패:** 객체와 이름 할당이 성공했는지, XArray 저장이 성공했는지 확인해야 한다. 등록하지 못했는데 전체 횟수만 증가하면 항목별 합계와 전체 횟수가 달라질 수도 있다.

**출력·해제 중인 객체의 수명:** 다른 실행 흐름이 아직 집계 중인데 객체를 출력하거나 해제하면 안정된 결과나 유효한 포인터를 보장하기 어렵다. 계측이 끝난 뒤 접근이 더 없다는 조건을 마련해야 한다.

따라서 원자적 카운터 증가만으로 전체 정확성이 해결되지는 않는다. 중복 등록 처리, 실패 정책, 객체 수명, 통계를 읽는 시점을 함께 설계해야 한다. XArray 문서도 저장한 객체의 보호에는 별도의 참조·잠금 규칙이 필요함을 설명한다. [Linux 5.4 XArray의 Locking](https://www.kernel.org/doc/html/v5.4/core-api/xarray.html#locking)

## 13. 과제의 측정값은 CPU별 함수 호출 비율이다

*Practical Class 10, 33~48쪽*

자료는 먼저 PID·태스크 이름을 이용해 `wb_check_background_flush()`의 특정 경로를 집계하는 예를 보여 준다. 이어 과제에서는 키를 CPU 번호로 바꾸고 `pxt4_file_write_iter()`가 각 CPU에서 몇 번 호출되는지 센다.

계측 위치도 측정값을 결정한다. 자료의 `wb_check_background_flush()` 예에서는 조건문 안에 집계가 있으므로 **그 조건을 통과해 계측 지점을 실행한 횟수**가 쌓인다. 함수에 진입한 모든 횟수라고 단정하면 안 된다.

과제 제목은 “Checking CPU utilization”이지만, 실제로 요구하는 출력은 다음 세 항목이다.

1. CPU 번호
2. 해당 CPU에서의 `pxt4_file_write_iter()` 호출 횟수
3. 전체 호출 횟수에서 차지하는 비율

이 비율은 **CPU 사용 시간의 비율이 아니다.** CPU 0이 전체 호출의 30%를 처리했다고 해서 CPU 사용률이 30%라거나 전체 실행 시간의 30%를 소비했다는 뜻은 아니다. 호출마다 처리 시간이 다를 수 있고 다른 작업도 존재한다.

자료 48쪽은 `current`로 현재 태스크를 얻고 `current->cpu`로 CPU 번호를 읽는 예를 제시한다. 이는 수업 코드 환경의 표현이다. 다른 커널이나 아키텍처에서는 필드 존재와 지원 API를 확인해야 하며, CPU 번호를 읽은 뒤 실행이 다른 CPU로 이동할 수 있다는 점도 계측 시점의 정의에 포함해야 한다.

### fio 조건 읽기

과제의 조건은 buffered sequential write, 4KiB 블록, CPU 코어 수에 맞춘 job 수, 전체 쓰기 크기는 RAM의 3배다. `direct=0`은 buffered I/O를 뜻한다.

**설명용 계산:** RAM 4GiB, job 4개라면 전체 12GiB를 쓰도록 job별 `size`를 3GiB로 둔다.

$$
\text{job별 크기}=\frac{\text{RAM 크기}\times3}{\text{numjobs}}.
$$

`size=12G`를 job마다 주면 전체가 48GiB가 되어 조건과 달라진다. 과제의 테스트 장치는 전체 쓰기 크기보다 넉넉한 여유 공간이 필요하다. 또한 여러 job을 띄운다는 설정만으로 각 job이 특정 CPU에 고정되는 것은 아니다.

이 조건에서 12GiB를 4KiB 단위로 나눈 산술적 I/O 수는 3,145,728회다. 다만 모든 실행에서 이 수가 계측한 커널 함수 호출 횟수와 반드시 같다고 보장하지는 않는다. 실제 I/O 경로·반환 결과·계측 위치를 함께 확인해야 한다.

### 강의 출력 예제 해석

아래 수치는 **실습 자료 47쪽의 예시 출력**이다.

| CPU | 호출 횟수 | 자료의 정수 비율 |
|---|---:|---:|
| 0 | 839,701 | 26% |
| 1 | 854,459 | 27% |
| 2 | 641,532 | 20% |
| 3 | 810,036 | 25% |
| 합계 | 3,145,728 | 98% |

비율의 합이 98%인 이유는 각 항목의 정수 나눗셈에서 소수 부분이 잘리기 때문이다. 호출 횟수의 합은 출력의 전체 횟수와 일치한다. 이것은 해당 출력의 일관성을 확인하는 근거지만, 모든 실행에서 경쟁이나 누락이 없다는 증명은 아니다.

자료 46쪽처럼 마지막 로그 몇 줄에 CPU 3만 보이는 경우도, 전체 작업을 CPU 3이 모두 처리했다는 뜻은 아니다. 로그 끝부분만 보고 있으며 링 버퍼의 오래된 내용은 밀려났을 수 있다. 키별 집계가 필요한 이유다.

## 14. 복습문제

<details><summary>1. 같은 가상주소를 다시 읽는데 물리 프레임이 바뀔 수 있는가?</summary>

가능하다. 커널이 페이지 내용을 회수·재적재하거나 이동한 뒤 페이지 테이블의 연결을 갱신하면 프로세스는 같은 가상주소를 계속 사용할 수 있다.

</details>

<details><summary>2. Clean file-backed page를 회수할 때 swap이 꼭 필요한가?</summary>

일반적인 파일 캐시라면 원래 파일에서 다시 읽어 올 수 있으므로 반드시 필요하지 않다. 익명 페이지와 파일 페이지의 backing store 차이를 구분한다.

</details>

<details><summary>3. struct page 포인터와 페이지 데이터의 포인터는 같은가?</summary>

아니다. 전자는 물리 프레임의 관리 정보를 가리킨다. 프레임 내용에 접근하는 매핑의 가상주소와 구분해야 한다.

</details>

<details><summary>4. 4KiB 페이지에서 PFN 7의 시작 물리주소는?</summary>

`7 × 4096 = 28672`, 즉 `0x7000`이다. 이 정수를 포인터로 캐스팅하는 것만으로 물리 메모리에 직접 접근할 수 있는 것은 아니다.

</details>

<details><summary>5. TLB miss가 나면 반드시 page fault가 발생하는가?</summary>

아니다. 페이지 테이블에 유효하고 권한을 만족하는 매핑이 있으면 테이블 탐색으로 변환을 얻을 수 있다.

</details>

<details><summary>6. Canonical address이면 접근 가능한 주소인가?</summary>

주소 형식 조건만 만족한다. 실제 매핑과 접근 권한이 있는지는 별도로 확인해야 한다.

</details>

<details><summary>7. XArray의 64슬롯 노드에서 인덱스 67은 어떤 경로인가?</summary>

`shift=6`인 상위 노드의 슬롯 1에서 `shift=0`인 하위 노드로 내려간 뒤 슬롯 3을 고른다. 전제는 본문의 0~4095를 다루는 두 단계 구조다.

</details>

<details><summary>8. xa_store와 xa_insert의 가장 중요한 차이는?</summary>

`xa_store`는 기존 항목을 교체할 수 있다. `xa_insert`는 해당 인덱스가 이미 차 있으면 `-EBUSY`를 반환한다.

</details>

<details><summary>9. 카운터 증가가 원자적이면 최초 객체 등록 경쟁도 해결되는가?</summary>

아니다. 두 실행 흐름이 동시에 없는 키를 관찰하고 서로 다른 객체를 등록하는 문제는 별개다. 복합 연산의 동기화와 객체 수명을 함께 다뤄야 한다.

</details>

<details><summary>10. CPU별 호출 비율의 합이 98%이면 반드시 호출이 누락된 것인가?</summary>

아니다. 각 비율을 정수로 잘라 출력하면 합이 100%보다 작을 수 있다. 우선 원시 호출 수의 합과 전체 횟수를 비교한다. 반대로 합이 맞는다는 것만으로 모든 동시성 문제가 없다고 결론 내리지도 않는다.

</details>
